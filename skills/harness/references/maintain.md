# Maintain — keep the skill and its map honest

A feature map rots the moment the app changes. This is the upkeep loop for a skill generated by `/harness`, or any project-local verification skill with a feature map. The unit of rigor is the feature: every feature file gets source coverage and one live drive, without terminalising every bullet.

## Outcomes — pick one, say which

- **clean** — every feature got source and live coverage; nothing worth shipping. No commit.
- **changed** — one commit of proven corrections, confined to the skill's own directory.
- **blocked** — coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only the verification skill's own directory: its `SKILL.md`, `features/`, its helpers. **Never product code.** Behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it and keep it out of this change — it becomes an idea (`factory docs idea add`) or a bugfix PRD).

## The pass

0. **Locate.** `.claude/skills/verify-*/`. Several → ask which. None → stop and point at `/harness`.
1. **Index hygiene.** The README lists exactly the sibling files. Fix missing, extra, duplicate and dead entries. Lightweight; no generated inventory.
2. **Source wave.** One read-only Explore agent per feature file, launched together in one message, on the **`mechanical`** model from [_shared/models.md](../../_shared/models.md) — this is bulk reading whose answer is a list, and the fan-out equals the feature count. Each answers "how does this user-facing feature work?" from source, flags likely drift with `file:line`, and returns one concise live recipe. Agents never drive the app and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe.
3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; do not re-prove clean claims. Sweep recent churn — `git log --since` on routes, controllers, pages, commands — for user-facing surfaces missing from the map. A concrete source path is required before calling one missing.
4. **Live pass.** Required even when source looks clean. You drive, serially, following the skill's own Launch model — one long-lived instance for servers and UIs, a fresh isolated session per drive for short-lived CLIs. Every feature at least once. Three invariants hold whatever fails:
   - **Doctor before the first drive and after any failed one.** Where doctor cannot see the failure (a wedged UI on a healthy process), reset to a known state or relaunch rather than hoping.
   - **Evidence captured so far survives every cleanup**, checked at its named path, not assumed.
   - **Nothing a drive started outlives its usefulness.** Failed-iteration residue is cleaned whether the session is stuck, exited or shared — for a shared instance, clean the residue, not the instance.

   A doctor failure caused by skill drift is drift: fix it under edit scope and retry once, restarting only what the fix invalidated, before calling the pass `blocked`. A feature that cannot be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted; a map that omits that prerequisite is drift. Any helper fix from triage is re-driven live before it ships. Final teardown after the last drive, including those re-proofs.
5. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the harness cannot drive → harness gap, fix it (helpers executable, invocation in the body). App behavior actually broken → product gap: record it for the user, keep it out of this change.
6. **Ship or stop.** `changed` → one commit, every changed file re-read first. `clean` or `blocked` → no commit; report the outcome and the coverage honestly.

Run notes — features covered, unreachable prerequisites, confirmed drift, outcome — go in the scratchpad, never committed.
