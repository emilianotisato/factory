Sources: [create-verification-skill](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md) and [maintain-verification-skill](https://github.com/cursor/plugins/blob/main/pstack/skills/maintain-verification-skill/SKILL.md) (last change 4483dcd, 2026-07-30). `harness` (then `verify-app`) already descends from the first: same interview, Launch / Doctor / Drive / Evidence / Cleanup, feature map, prove-once step, and `references/maintain.md` has the clean / changed / blocked outcomes, the edit scope and the drift / harness-gap / product-gap triage. Not in ours yet: (1) proof standards in Evidence: drive the real user path, never test-only endpoints; capture the action and the resulting state; check side effects (rows, files, messages); mocks only at a production boundary; check what a dry-run mode really skips by watching files, network and git refs. (2) The maintain pass's source wave: one read-only subagent per feature file, run at once, each returning summary / entry points / drift with citations / one live recipe, merged before a single serial live pass. (3) The live pass's three invariants: doctor before any drive after a surprise, evidence survives every cleanup (checked, not assumed), nothing a drive started outlives it. (4) `verified-unreachable` needs the concrete prerequisite and the route tried. (5) At most one PR of proven corrections per pass. Why: the owner wants both analysed and the useful concepts copied.
