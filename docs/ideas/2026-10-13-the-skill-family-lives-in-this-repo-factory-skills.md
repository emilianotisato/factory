Decided 2026-10-13 during the PRD-002 revision: **this is PRD-004, built after 002.** The owner wants the skills held here as the source, installed into a repo (`.claude/skills`, and the Codex and Cursor equivalents) or the user dir, and updated by `factory` when the framework evolves, in full coordination with the binary. Recon (2026-10-13): `~/.claude/skills` symlinks to `~/Dropbox/dev/claude-code-skills`, a git repo with no remote (486 files, 13 MB with `synced/`); the family is deliver 56K, feature-docs 260K, guardrails 40K, polish 20K, prd 28K, prd-to-tasks 28K, test-cleanup 16K, ux-review 28K, verify-app 52K, about 530 KB; `skills/factory-deliver` already lives here and is symlinked out, the pattern to generalise. Questions for the PRD: copy or symlink per target; how a repo pins a skill version against the binary's; whether `caveman`, `codex` and the other non-family skills stay in Dropbox; what `docs doctor` says when the installed family is older than the binary. PRD-002 FR-17 edits the 23 `docs.mjs` lines in place first; 004 redoes them as in-repo files.

**Recon for the PRD interview, 2026-10-13, paused by the owner for a content review first.** Three retros (001, 002, 003) each wrote a "Framework friction → skills repo" section, about twelve concrete edits in all; none was applied in the Dropbox repo (the 30-file second-opinion limit flagged twice, `polish` §9 still tells an unattended worker to commit, the retro template still names `measure.py`). So the retro-to-skill loop has no destination, and PRD-004 must give it one: the machinery (manifest with binary version and per-file hash, `doctor` says behind or hand-edited, `skills update` re-renders and refuses over a hand edit) plus the feedback path (the friction section lands as an idea in this repo for the owner, as a project overlay plus a printed issue link for a non-contributor). The family has no personal paths; the only personal facts are in `feature-docs/models.md`, which is the one case for a user-scope overlay. Siblings link `../feature-docs/models.md` 8 times and `../feature-docs/autonomy.md` 6 times. Lean on install: no choice offered, rendered into the repo and committed by `factory init`; the user scope holds overlays only. **Order: the owner reviews each skill interactively against the retros and the metrics first, edits land in the Dropbox repo, then PRD-004 ports the result.**

**From the polish review, 2026-10-13, for the PRD-004 interview.** `polish` is settled: keep the name; its six `Unattended (/deliver)` markers are gone and one line at the top says the pack's contract wins inside a run, so the contract is the only copy of the unattended rules. One FR candidate for this PRD: **`factory review second`**, the cross-vendor second opinion as a binary command. It probes auth before spending anything (`cursor-agent --list-models`), splits the diff into passes of about 600 changed lines or one module, streams findings so a timeout keeps what it found, and prints the findings for the skill to triage. Three retros hit the 900 s empty timeout and the silent auth expiry; the skill now carries a prose stopgap (600-line passes, probe first) until the command exists. The fixer worktree recipe moved to the lanes idea; the rest of collect (picking reviewers from the diff) is its own idea.

**From the feature-docs review, 2026-10-13: the skill is eliminated.** Its spec half is what `factory docs init` already writes into `docs/index.md`; its tool half described v2. Two binary items for this PRD: (1) `factory docs init` appends the convention block to `CLAUDE.md` and `AGENTS.md` (creating them if absent, mirroring when they are twins or symlinks) and prints the setup order: gate (`/guardrails`), harness (`/harness`), rubric (`/ux-review rubric`); (2) the installer ships `models.md` as one shared file beside the skills, split in two: the roles table is base and committed, the Cursor path, default model and rate-limit note are user scope in `~/.config/factory/`, never in the repo. `/prd` preflight now carries the setup order in prose. `autonomy.md` has one copy, `assets/`. `MAINTAINING.md` is imported as `docs/reference/skills-decisions.md`, history only. Ad-hoc migration (`PLAN.md`, `specs/`) is dropped: a new repo starts with `init`. Names so far: `prd-to-tasks` → `prd-to-slices`; prefix rule still open.

**From the slice review, 2026-10-13: names settled, set A.** The family uses its own vocabulary, bare, no prefix: `/prd`, `/slice` (was `prd-to-tasks`, renamed in Dropbox at e85e4a4), `/deliver` (was `factory-deliver`), `/polish`, `/gate` (was `guardrails`), `/harness` (was `verify-app`), `/ux` (was `ux-review`), `/prune` (was `test-cleanup`). Each pending rename lands at that skill's review. Two consequences for the installer: it refuses a name collision with a skill the project already has, and `src/pack.rs` `for_polish` keeps spawning `/polish` unchanged. The `ft-` and `factory-` prefixes were weighed and dropped: grouping is not worth a prefix nobody can read. Also from this review: slicing is attended and happens before a run, so `slice` carries no contract line and no unattended markers; the skill's `template.md` is deleted because `assets/docs/slice.scaffold.md` is the template; the size cap is gone from the skill, with its retirement from the binary parked as its own idea.

**From the prd review, 2026-10-13.** `prd` is v3 now (Dropbox 2b29e14): no frontmatter status or FR ranges, `summary:` replaces the index Notes cell, FR ids are feature-scoped, `template.md` deleted because `assets/docs/prd.scaffold.md` is the template, and the scaffold's §2 is Blast radius. The dead v2 `deliver` is removed from Dropbox and the cockpit skill is `skills/deliver` here, symlinked as `/deliver`. For the installer: `/deliver` is the one skill that lives in this repo's `skills/` rather than the family dir, and the one the README points at.

**From the gate review, 2026-10-13.** `guardrails` → `gate` (Dropbox, this repo's messages in `check.rs`, `preflight.rs`, `scaffold.rs`, `gate.rs`, `assets/retro.md`). Remaining renames: `verify-app` → `harness`, `ux-review` → `ux`.
